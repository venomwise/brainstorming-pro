# Clarify Workflow UX Fixes Design

## Summary

We will fix the `/clarify` first-run and clarification startup experience so users can reliably move from a natural-language request, including Chinese requests, to an actual reviewable `design.md`. The change improves first-run model selection prompts, replaces unreadable Chinese topic slug fallbacks with LLM-generated English kebab-case topic candidates, and connects the `/clarify` workflow phases to real discovery/design/gate execution instead of only advancing state metadata.

## Goals

- First-run setup clearly tells users to select models by number, not by model name.
- Topic candidates are always safe English kebab-case slugs derived from the project or feature name, for example `task-dispatch-status`.
- Chinese or mixed-language requests receive 2-3 English kebab-case topic candidates generated by the configured model.
- The system never generates unreadable codepoint fallback slugs such as `topic-itv-g99-i61`.
- If topic generation fails or yields no valid candidates, the user is asked to enter an English kebab-case topic manually.
- After topic confirmation, `/clarify` runs the actual V0 discovery/design phase, writes the expected design artifacts, and presents a design review gate.
- Final approval provides the lifecycle handoff command `/spec-plan <topic>` without auto-running planning.

## Primary Users / Roles

- **End users running `/clarify`**: want a guided clarification workflow that works for Chinese and English requests without needing to understand internal artifact state.
- **Chinese-language users**: want to write the request naturally in Chinese while still getting repository-compatible English kebab-case spec paths.
- **Package maintainers**: need deterministic safety checks, clear recovery behavior, and tests that prevent regressions in workflow lifecycle behavior.

## Non-Goals

- Build a full custom TUI selector for first-run model selection in this change. The prompt will be improved now; selector UX can be a later enhancement.
- Support Chinese topic directory names. Topics should be English kebab-case regardless of request language.
- Maintain or expand a static Chinese-to-English glossary for topic naming.
- Auto-run `/spec-plan` after design approval.
- Implement `/spec-exec` or planning changes beyond ensuring the clarify handoff remains correct.
- Change the public command surface of `/clarify`, `/spec-plan`, or `/spec-exec`.

## Context

Brainstorming Pro is a Pi package for recoverable clarification workflows. Core code lives under `extensions/clarification-orchestrator/`, with command handlers in `commands/`, phase implementations in `phases/`, topic proposal in `topic-proposal.ts`, first-run setup in `first-run-config.ts`, and workflow state in `workflow.ts` / `artifact-store.ts`.

Current behavior has three issues:

1. `first-run-config.ts` displays discovered models but the input prompt does not strongly communicate that users must enter numeric choices.
2. `topic-proposal.ts` uses a small `chineseGloss` map and falls back to per-character codepoint slugs for uncovered Chinese text, producing unreadable candidates such as `topic-itv-g99-i61-fim...`.
3. `workflow.ts` currently advances through phase names (`REQUEST_CAPTURE`, `TOPIC_PROPOSAL`, `TOPIC_CONFIRMATION`, `V0_BRAINSTORMING`, `DESIGN_REVIEW_GATE`) without invoking phase handlers such as `runDiscoveryPhase()` or user gates such as `presentDesignReviewGate()`. As a result, runs can stop at `DESIGN_REVIEW_GATE` with no `design.md` and zero agent runs.

The repository README states that lifecycle boundaries are explicit: `/clarify` creates an approved `design.md`, then prints `/spec-plan <topic>` for the user to run manually.

## Discovery (recommended for non-trivial or ambiguous requirements)

### Key Discoveries

- The apparent Chinese “garbling” is not an encoding problem; it is an intentional codepoint fallback in `translateChinesePhrase()`.
- The existing path guard allows Unicode letters, which permits Chinese directories. The desired rule is stricter for clarification topics: English kebab-case derived from the feature/project name.
- LLM-based topic naming is preferable to expanding a static Chinese glossary because topic naming requires semantic understanding of arbitrary user requests.
- LLM topic proposal depends on model configuration, so first-run setup must happen before topic proposal for requests that need semantic translation.
- The sample run under `temp/user-001/` confirms that the workflow reached `DESIGN_REVIEW_GATE` with `agentRuns: 0` and without design artifacts, showing the phase execution gap.

### Scope Decisions

- Include stricter topic candidate validation for English kebab-case.
- Include LLM topic proposal for Chinese/mixed-language requests.
- Include manual fallback when generated candidates are invalid or unavailable.
- Include workflow orchestration changes to execute V0 design and design gate behavior.
- Exclude full selector UI because it is an enhancement, not required to unblock the workflow.

## Proposed Solution

Implement a request startup pipeline that first ensures model configuration, then generates safe English topic candidates, then runs the actual clarification phase handlers after topic confirmation. The recommended approach is to keep the existing command and artifact model but replace placeholder phase transitions with concrete orchestration for the initial design lifecycle.

### Architecture

The clarified `/clarify` startup flow will have four layers:

1. **First-run configuration layer**
   - Ensures a provider-qualified default model exists.
   - Improves prompts so users know they must enter numeric choices.

2. **Topic proposal layer**
   - Uses deterministic English kebab-case extraction for English requests where possible.
   - Uses an LLM topic proposal helper for Chinese or mixed-language requests.
   - Validates all candidates against a strict English kebab-case policy.
   - Falls back to manual entry instead of unsafe or unreadable slug generation.

3. **Workflow orchestration layer**
   - Creates run artifacts after topic confirmation.
   - Runs V0 discovery/design through the designer agent.
   - Presents the design review gate using the generated `design.md`.

4. **Lifecycle handoff layer**
   - On approval, writes final approval artifacts and prints `/spec-plan <topic>`.
   - On review/revise/save, routes to the corresponding existing phase or resumable state.

### Components

- **`first-run-config.ts`**
  - Update notify/input copy to explicitly say “enter the number shown in the list”.
  - Preserve current config file shape and provider-qualified model validation.

- **`topic-proposal.ts`**
  - Remove static `chineseGloss` translation and codepoint fallback behavior.
  - Add strict topic slug validation for generated candidates: lowercase English letters, numbers, hyphens, no leading/trailing hyphen, no repeated hyphen.
  - Keep deterministic candidate generation for already-English input.
  - Expose a path for externally generated candidates so command orchestration can combine LLM proposals with validation and existing-topic conflict checks.

- **New topic proposal helper, likely `topic-proposal-agent.ts` or equivalent**
  - Builds a compact prompt asking the configured model to return JSON with 2-3 English kebab-case topic candidates.
  - Instructs the model to derive names from the feature/project meaning, not translate word-for-word.
  - Parses and validates output before it reaches the user.
  - Does not create artifacts or directories by itself.

- **`commands/clarify.ts`**
  - Ensures first-run config before topic proposal.
  - Chooses deterministic vs LLM topic proposal based on request language/content.
  - Calls topic confirmation with only valid English kebab-case candidates.
  - After run creation, invokes the real workflow orchestration rather than only phase transitions.
  - Prints actionable completion or resume messages.

- **`workflow.ts` or a dedicated orchestrator module**
  - Replace or supplement simple phase transition loops with concrete phase execution.
  - On `V0_BRAINSTORMING`, call `runDiscoveryPhase()` using the discovered designer agent.
  - On `DESIGN_REVIEW_GATE`, call `presentDesignReviewGate()` with the latest design version.
  - Route gate actions:
    - `approve`: run final approval and complete, then print `/spec-plan <topic>`.
    - `review`: run cross-review/triage/decision/refine/verify loop according to existing lifecycle rules.
    - `revise`: enter conversational revision and return to gate.
    - `save`: persist resumable state and stop.

- **`path-guard.ts` or topic-specific validator**
  - Preserve general path traversal protections.
  - Add a stricter clarification topic validator if other code still needs broader Unicode path support.

### Data Flow

1. User runs `/clarify <request>`.
2. Command loads config.
3. If no user/project config exists, first-run setup lists Pi models and asks for numeric model choices with clearer prompt text.
4. Command determines topic proposal mode:
   - English request: deterministic English kebab-case candidates.
   - Chinese/mixed request: LLM generates candidate JSON.
5. Topic proposal validation filters candidates to strict English kebab-case only.
6. If no valid candidates remain, the user is asked to manually enter an English kebab-case topic.
7. User confirms a candidate or enters a manual topic.
8. Command creates `specs/<topic>/clarification/run-*` artifacts.
9. Workflow runs designer discovery/design and writes:
   - `specs/<topic>/design.md`
   - `specs/<topic>/clarification/run-*/versions/v0/design.md`
   - discovery artifacts
   - updated `metadata.json` and `state.json`
10. Workflow presents the design review gate.
11. User chooses `approve`, `review`, `revise`, or `save`.
12. On approval, final approval artifacts are written and the command prints `/spec-plan <topic>`.

## Error Handling

- **No interactive UI**: non-dry-run `/clarify` continues to fail early with guidance because topic confirmation and design gates require interaction.
- **No first-run model config**: first-run setup runs before topic proposal. If model discovery fails, existing `/clarify-doctor` guidance remains.
- **User enters model name instead of number**: return a clear error: “Enter the number from the list, for example `1`, not the model name.”
- **LLM topic proposal fails**: notify the user that automatic English topic generation failed and request manual English kebab-case entry.
- **LLM returns invalid topic names**: filter invalid candidates; if all are invalid, request manual entry.
- **Manual topic invalid**: reject with an explicit English kebab-case format message and allow retry if the surrounding UI supports it.
- **Designer subagent fails**: record a workflow error, mark the run recoverable or aborted according to existing subagent failure policy, and print a resume/status hint.
- **Design gate called without design artifacts**: treat as an orchestration error; do not claim the workflow reached a reviewable gate.
- **Approval with unresolved blocking decisions**: preserve existing blocking issue checks.

## Testing

- **Unit tests: first-run setup**
  - Prompt text includes “number” / “编号” semantics.
  - Invalid model-name input produces a clear numeric-choice error.

- **Unit tests: topic validation**
  - Accepts `task-dispatch-status`, `payment-integration`, `user-auth-v2`.
  - Rejects Chinese text, spaces, underscores, uppercase, path separators, leading/trailing hyphens, repeated hyphens, and empty values.

- **Unit tests: topic proposal**
  - Chinese requests do not produce codepoint slugs.
  - LLM output is filtered to valid English kebab-case candidates.
  - Empty/invalid LLM output triggers manual fallback.
  - Existing topic conflicts and similar topics are still represented safely.

- **Integration tests: `/clarify` startup**
  - First-run config completes, then Chinese request receives LLM-generated English candidates.
  - User confirms a candidate and artifacts are created under `specs/<english-topic>/`.

- **Integration tests: workflow execution**
  - Topic confirmation leads to designer execution (`agentRuns > 0` with a mocked runner).
  - `design.md` and `versions/v0/design.md` are written before entering design gate.
  - Gate `save` leaves `resumeStatus: awaiting-design-gate-decision`.
  - Gate `approve` writes final approval and prints `/spec-plan <topic>`.

- **Security tests**
  - LLM-generated malicious topics such as `../x`, `/tmp/x`, `foo/bar`, `.hidden`, or Unicode homoglyph attempts are rejected.
  - Project-local config trust and debug redaction behavior remain unchanged.

## Open Questions

- Should the manual topic prompt retry on invalid input in the same command invocation, or fail once and ask the user to rerun? Recommended: retry up to a small fixed number, then fail clearly.
- Should LLM topic proposal use the normal designer agent runner or a smaller internal prompt runner? Recommended: use the same configured default model through the existing subagent infrastructure where practical, but keep the prompt/tool access minimal.
- Should the design gate initially keep text input (`approve/review/revise/save`) or use a selector? Recommended: keep text input in this change and consider selector UI later.
