# Requirements Document: Design Review Triage and Readiness

## Introduction

Design Review Triage and Readiness adds a deterministic interpretation layer after the existing Brainstorming Pro design review aggregate. It consumes version-bound design review runs, normalized findings, reviewer coverage, basic readiness, and durable ledger refs, then produces a structured triage report that explains which findings are duplicate issues, which findings conflict, which issues are must-fix, should-fix, or notes, and whether approval readiness is ready, blocked, incomplete, failed, skipped, or stale.

The system solves the gap between raw multi-reviewer findings and actionable workflow decisions for workflow users, maintainers, future design revision agents, and UX/TUI renderers. It remains inside the existing `/brainstorm-pro` runtime, review ledger, artifact binding, and approval gate model. It does not execute reviewers, retry failures, accept incomplete reviews, mutate `design.md`, revise artifacts, or approve design.

## Glossary

- **Triage report**: A durable JSON report that classifies and explains review findings for one exact design review run and design artifact version.
- **Finding cluster**: A deterministic group of one or more source `DesignReviewFinding` records that describe the same underlying issue.
- **Must-fix**: A triage level for issues that block approval readiness or must be resolved before safe planning.
- **Should-fix**: A triage level for issues that should be addressed but do not independently block approval readiness.
- **Note**: A triage level for informational, optional, or low-risk observations.
- **Conflict**: A detected disagreement between reviewer findings, such as incompatible recommendations or severity disagreement.
- **Unresolved user question**: A reviewer-provided question that may require user input before approval or revision.
- **Coverage summary**: A readiness sub-report describing selected, unselected, succeeded, failed, and pending-retry reviewers.
- **Source binding**: The exact design artifact ref plus aggregate, coverage, and reviewer-result refs/checksums that a triage report was generated from.
- **Stale triage**: A triage report whose source aggregate, coverage, reviewer results, or design artifact no longer matches the current durable review evidence.
- **Enhanced readiness**: The coverage-aware readiness report generated by triage; it advises next actions but never approves design.

## Requirements

### Requirement 1: Triage Engine and Source Binding

**User Story:** As a maintainer, I want triage to be bound to exact review evidence, so that stale or corrupted summaries cannot be reused for approval readiness.

#### Acceptance Criteria

1. WHEN a design review aggregate is durably available, THEN the system SHALL build a triage report for the same `reviewRunId` and exact `designRef`.
2. WHEN building triage, THEN the system SHALL record source aggregate path/checksum, optional coverage path/checksum, reviewer result refs, generation timestamp, and design artifact ref.
3. IF the review run, aggregate, readiness, coverage, or reviewer result evidence is missing, malformed, or inconsistent, THEN the system SHALL fail closed and SHALL NOT produce approval-ready triage.
4. IF an existing triage report source checksum differs from the latest aggregate, coverage, reviewer results, or design artifact checksum, THEN the system SHALL mark or treat the triage report as stale.
5. WHEN triage is stale, THEN the system SHALL NOT use its readiness to proceed to design approval and SHALL require rebuilding from current durable sources or a fresh review decision when the design changed.
6. WHEN triage runs for minimal, full, selected-subset, partial, skipped, or failed review results, THEN the system SHALL preserve the original review mode semantics and SHALL NOT reinterpret skipped, failed, or incomplete reviews as passed.

### Requirement 2: Finding Deduplication and Clustering

**User Story:** As a workflow user, I want duplicate reviewer findings grouped, so that I can understand the underlying issues without losing reviewer evidence.

#### Acceptance Criteria

1. WHEN multiple findings describe the same high-confidence issue, THEN the system SHALL merge them into one finding cluster.
2. WHEN findings are merged, THEN the cluster SHALL preserve all source finding ids, reviewer roles, evidence, affected sections, recommendations, and user questions.
3. WHEN deduplication confidence is low or ambiguous, THEN the system SHALL keep findings in separate clusters rather than risk hiding distinct issues.
4. WHEN a cluster contains multiple severities, THEN the cluster severity SHALL be the highest source severity using `blocking > non-blocking > note`.
5. WHEN a cluster is generated, THEN its cluster id SHALL be deterministic for the same source finding set.
6. IF a finding id referenced by a cluster is absent from the source aggregate, THEN the system SHALL reject the triage report as inconsistent.

### Requirement 3: Conflict Detection

**User Story:** As a reviewer or future reviser, I want reviewer disagreements surfaced explicitly, so that important trade-offs are not silently discarded.

#### Acceptance Criteria

1. WHEN findings for related sections or issues contain incompatible recommendations, THEN the system SHALL record a `recommendation-conflict`.
2. WHEN findings for related issues materially disagree on severity, THEN the system SHALL record a `severity-disagreement`.
3. WHEN findings disagree about expanding versus trimming scope, THEN the system SHALL record a `scope-disagreement`.
4. WHEN one finding indicates readiness while another related finding raises a lifecycle, gate, security, or artifact-binding blocker, THEN the system SHALL record a `readiness-disagreement`.
5. WHEN a conflict affects security, path guards, artifact binding, approval gates, state authority, stale artifacts, or scope correctness, THEN the system SHALL mark the conflict impact as blocking approval readiness or requiring resolution before revision.
6. WHEN conflicts are detected, THEN the system SHALL preserve the source finding ids and SHALL NOT automatically choose one reviewer recommendation as authoritative.

### Requirement 4: Triage Classification

**User Story:** As a workflow user, I want findings separated into must-fix, should-fix, and notes, so that I can decide what blocks approval and what can be deferred.

#### Acceptance Criteria

1. WHEN a cluster includes any blocking source finding, THEN the system SHALL classify the cluster as `must-fix`.
2. WHEN a non-blocking cluster requires revision and affects lifecycle gates, artifact binding, path/trust boundaries, state authority, approval safety, or unrecoverable runtime behavior, THEN the system SHALL classify it as `must-fix`.
3. WHEN a cluster contains a user question that changes scope, architecture, requirements, data model, or security assumptions, THEN the system SHALL classify it as `must-fix` and mark the question as blocking approval readiness.
4. WHEN a cluster is non-blocking but has meaningful planning, consistency, context, or testing value, THEN the system SHALL classify it as `should-fix`.
5. WHEN a cluster is informational, optional polish, future enhancement, or low-risk observation, THEN the system SHALL classify it as `note`.
6. IF a high-risk conflict is attached to a cluster, THEN the system SHALL not classify that cluster below `must-fix` unless deterministic rules prove the conflict is informational.

### Requirement 5: Unresolved Question and Coverage Summary

**User Story:** As a user resuming a workflow, I want unanswered questions and reviewer coverage explained, so that I know whether to revise, retry, accept incomplete, or approve.

#### Acceptance Criteria

1. WHEN source findings contain `userQuestion`, THEN the system SHALL extract them into unresolved question records linked to source finding ids.
2. WHEN duplicate or equivalent user questions exist, THEN the system SHALL group them without losing source finding ids.
3. WHEN a user question affects scope, architecture, requirements, data model, security, lifecycle gates, or approval safety, THEN the system SHALL mark it as blocking approval readiness.
4. WHEN coverage exists, THEN the system SHALL include selected, unselected, succeeded, failed, and pending-retry reviewers in the coverage summary.
5. WHEN reviewers are unselected, THEN the system SHALL show them as unselected and SHALL NOT count them as failed or missing.
6. WHEN selected reviewers failed and at least one selected reviewer succeeded, THEN the coverage summary SHALL identify the review as incomplete.

### Requirement 6: Enhanced Readiness Report

**User Story:** As a workflow user, I want a clear readiness report with recommended next actions, so that I can safely proceed without confusing review readiness with approval.

#### Acceptance Criteria

1. WHEN source readiness is `skipped-by-user`, THEN enhanced readiness SHALL remain `skipped-by-user` and include an explicit skip caveat.
2. WHEN source readiness is `failed`, THEN enhanced readiness SHALL remain `failed` and recommend inspecting failure or retrying failed reviewers when coverage supports retry.
3. WHEN source readiness is `incomplete-review` and triage has no must-fix cluster, no blocking conflict, and no blocking question, THEN enhanced readiness SHALL remain `incomplete-review` and recommend `accept-incomplete-or-retry`.
4. WHEN source readiness is `incomplete-review` and triage has any must-fix cluster, blocking conflict, or blocking question, THEN enhanced readiness SHALL be `blocked`.
5. WHEN any must-fix cluster exists, THEN enhanced readiness SHALL be `blocked` and SHALL recommend `revise-design` or `resolve-user-questions`.
6. WHEN no must-fix clusters, blocking conflicts, or blocking questions exist and source readiness is passed, THEN enhanced readiness SHALL be `ready-for-user-approval` and recommend `approve-design`.
7. WHEN enhanced readiness recommends approval, THEN it SHALL NOT approve design, start planning, or bypass the separate design approval gate.
8. WHEN accepted incomplete has been recorded by Spec 5.2, THEN triage SHALL remain truthful about incomplete coverage and SHALL NOT rewrite the review as fully passed.

### Requirement 7: User-Facing Summary

**User Story:** As a workflow user or TUI viewer, I want a concise summary of review triage, so that I can understand the current state without reading raw JSON.

#### Acceptance Criteria

1. WHEN triage completes, THEN the system SHALL generate deterministic user-facing summary text from the structured triage report.
2. WHEN must-fix, should-fix, notes, conflicts, unresolved questions, or incomplete coverage exist, THEN the summary SHALL mention their counts or key implications.
3. WHEN readiness is blocked, incomplete, failed, skipped, or stale, THEN the summary SHALL NOT imply that the design is approved or fully ready.
4. IF optional agent-generated summary is introduced, THEN the agent output SHALL be prose-only and SHALL NOT change ids, tiers, conflicts, coverage, readiness, or next actions.
5. IF optional agent summary fails, is malformed, or attempts to alter structured fields, THEN the system SHALL reject it and use deterministic summary text.

### Requirement 8: Triage Ledger Persistence

**User Story:** As a maintainer, I want triage persisted in the review ledger, so that status, resume, audit, and revision can reconstruct the exact review interpretation.

#### Acceptance Criteria

1. WHEN triage completes successfully, THEN the system SHALL write `triage-report.json` under `specs/<topic>/.workflow/reviews/design/<review-run-id>/`.
2. WHEN writing triage or enhanced readiness, THEN the system SHALL use atomic writes and workflow path guards.
3. IF a triage ledger path would escape the review run directory, THEN the system SHALL reject the operation.
4. WHEN enhanced readiness is written, THEN the system SHALL either preserve backward compatibility for existing `readiness.json` consumers or store the enhanced readiness inside `triage-report.json` as the authoritative refinement.
5. IF triage ledger writing fails, THEN the system SHALL not treat triage/readiness as durable and SHALL fail closed.
6. WHEN status/resume reads triage, THEN the system SHALL validate source bindings before trusting the report.

### Requirement 9: Runtime and Recovery Integration

**User Story:** As a future UX or runtime implementer, I want status/resume to consume triage safely, so that users see actionable review state without expanding the public command surface.

#### Acceptance Criteria

1. WHEN design review produces or updates an aggregate, THEN the system SHALL run or refresh triage before exposing enhanced readiness when durable sources are valid.
2. WHEN retry updates effective reviewer results and aggregate evidence, THEN the system SHALL invalidate or rebuild previous triage.
3. WHEN design artifact changes after triage, THEN status/resume SHALL treat prior triage as stale for approval readiness.
4. WHEN triage readiness is blocked, THEN status/resume SHALL expose must-fix clusters, blocking questions, conflicts, and safe recovery hints without approving design.
5. WHEN triage readiness is incomplete, THEN status/resume SHALL preserve Spec 5.2 retry and accept-incomplete recovery action semantics.
6. WHEN triage readiness is ready-for-user-approval, THEN runtime SHALL still require the existing explicit design approval gate before planning.

### Requirement 10: Security and Authority Boundaries

**User Story:** As a security reviewer, I want triage inputs and summaries treated as untrusted, so that crafted files or LLM prose cannot bypass workflow gates.

#### Acceptance Criteria

1. WHEN triage input, ledger files, or summary files claim blockers disappeared, coverage changed, or failed reviewers succeeded, THEN the system SHALL validate against durable aggregate, coverage, reviewer results, design checksum, and state/event data.
2. WHEN crafted triage or readiness claims approval, planning, artifact mutation, or workflow transition authority, THEN the system SHALL reject or ignore those fields.
3. WHEN optional summary text implies approval contrary to structured readiness, THEN the system SHALL reject that summary or ensure structured readiness remains authoritative.
4. WHEN path traversal, spoofed design refs, checksum mismatch, corrupted source evidence, or stale source binding is detected, THEN the system SHALL fail closed.
5. WHEN triage completes, THEN it SHALL never mutate `design.md`, write approvals, record review decisions, accept incomplete, retry reviewers, or start planning.
6. WHEN runtime transitions occur after triage, THEN they SHALL use existing state-machine authorization and explicit user decisions rather than triage-provided instructions.
